# 2026-08-24: Add ActivityPub feed

Owner: Will Lachance <wlach@protonmail.com>

## Overview

### Problem Statement

It would be fun if posts to wrla.ch were syndicated to ActivityPub, so people
could subscribe to wrla.ch and receive compact post summaries in Mastodon or a
similar client.

### Context (as needed)

wrla.ch is a static site generated by a small Python program. Cloudflare Pages
is connected directly to the GitHub repository, builds the site, and serves the
contents of `_build`. Deployment configuration currently lives primarily in
the Cloudflare dashboard.

ActivityPub is not a pull-only feed format like Atom or RSS. A useful
implementation needs a discoverable actor and outbox, but it must also accept
`Follow` activities, remember followers, and actively deliver signed
activities to their inboxes. Replies arrive through the actor's inbox, and a
reply collection helps clients discover a more complete thread.

This is partly a learning project. The implementation should expose the
interesting parts of federation without turning wrla.ch into a general-purpose
social server. It should remain small enough to understand and should have a
realistic local integration test suite.

### Goals

- Let people follow `@wrlach@wrla.ch` and be notified of new blog posts.
- Make old posts visible through the actor's ActivityPub outbox without
  broadcasting the entire archive when federation is first enabled.
- Syndicate a compact announcement rather than the complete article. It will
  use the first prose paragraph, capped at 300 Unicode characters at a word
  boundary, followed by an ellipsis when article content was omitted and a
  link to the canonical post on wrla.ch.
- Track verified replies and expose them to ActivityPub clients without
  rendering them as comments on the blog.
- Let people like and boost posts from ActivityPub clients, and expose the
  resulting aggregate counts.
- Provide an explicit emergency-redaction mechanism for a federated post.
- Keep the design comprehensible, minimal, self-contained, and specific to
  wrla.ch.
- Keep Cloudflare configuration in this repository wherever Cloudflare
  supports configuration as code.
- Support useful local unit and integration testing without depending on live
  Fediverse services.

### Non-Goals

- Posting anything from wrla.ch other than announcements of new blog posts.
- Client-to-server ActivityPub posting.
- Multiple local actors.
- Private, direct, or followers-only posts.
- Rendering remote replies as comments on blog pages.
- Adding a follow button, copyable handle, remote-instance form, or other
  ActivityPub discovery UI to the blog.
- Initiating likes or boosts as the local actor, displaying a social
  interaction UI on wrla.ch, or notifying the author about each interaction.
- Supporting polls, reports, moderation tools, or arbitrary mentions.
- Federating ordinary edits to a post after its initial announcement.
- Perfect interoperability with every ActivityPub implementation.
- Being reusable for sites other than wrla.ch.

### Proposed Solution

Keep historical ActivityPub data in the static site and add a small Python
Cloudflare Worker for the stateful parts of federation.

The site generator will produce:

- The `@wrlach@wrla.ch` actor document and its public key.
- A paginated outbox containing every non-redacted post.
- A stable ActivityStreams `Note` for each post. The note will contain the post
  title, a compact excerpt of its first prose paragraph, and a visible link to
  the canonical article. When available, it will also attach the first
  meaningful image and its alt text.
- A manifest containing stable post identifiers, publication timestamps,
  ActivityPub object URLs, content hashes, and explicit tombstone entries.
- Tombstone objects for explicitly redacted posts.

The Worker will provide:

- WebFinger discovery for `acct:wrlach@wrla.ch`.
- An inbox supporting `Follow`, `Like`, `Announce`, their corresponding `Undo`
  activities, and public replies to known posts.
- Followers, replies, likes, and shares collections.
- Signed `Accept`, `Create`, and `Delete` delivery.
- A scheduled publisher with durable retry state.

Cloudflare D1 will store followers, observed posts, verified replies, likes and
announces, historical delivery recipients, and delivery attempts. The Worker's
RSA private key will be a Cloudflare secret; the corresponding public key will
be included in the actor document. Protocol logic will be Python. Cryptographic
operations will call the Workers Web Crypto API through Python Workers' Pyodide
FFI rather than implementing cryptography in Python.

Pydantic models will deserialize and validate data at protocol boundaries:
inbound activities, remote actors and keys, the deployed manifest and Notes,
and the repository-owned redaction configuration. ActivityPub models will
allow unknown extension fields while requiring the fields this implementation
uses; repository-owned formats will reject unknown fields and enforce their
cross-field invariants.

Substantial SQL result rows will use the same small boundary-validation
pattern without introducing an ORM or repository layer. Raw SQL remains next
to its callers and is converted to strict Pydantic models before application
logic consumes it. These models declare only the fields application logic
uses and tolerate other result columns, avoiding duplication of the complete
table schema. Small projections such as counts, identifiers, and metadata
values remain scalars; result models are introduced only where code otherwise
passes around a multi-column dictionary. Migration and model tests provide
the runtime checks that Pydantic and Python's type checker cannot derive from
raw SQL text.

The Worker will poll the manifest served by the production Pages deployment.
A post becomes eligible for delivery 15 minutes after the Worker first observes
it. Immediately before delivery, the Worker will fetch the latest deployed
ActivityPub object, so edits made during the grace period are included. Removing
a pending post cancels delivery. A later deployment does not restart the grace
period.

Polling the deployed site, rather than GitHub or the Pages build process, means
that a failed build cannot federate a post and that every advertised URL is
already publicly reachable.

## Detailed Design (as needed)

### Identity and URLs

The actor's WebFinger identity will be `acct:wrlach@wrla.ch`. Stable endpoints
will follow this general layout:

```text
/.well-known/webfinger
/activitypub/wrlach
/activitypub/wrlach/inbox
/activitypub/wrlach/outbox
/activitypub/wrlach/followers
/activitypub/posts/<source-id>
/activitypub/replies/<source-id>
/activitypub/likes/<source-id>
/activitypub/shares/<source-id>
```

`<source-id>` is the existing timestamp-and-slug source directory name. It is
already unique and remains stable if the public blog URL layout changes.

The actor will have type `Service`, a display name matching the blog, a profile
URL pointing to wrla.ch, the existing site icon, and links to its inbox,
outbox, followers collection, and public key.

### Post representation

The ActivityPub object is an announcement of an article, not a copy of the
article. It will use the first-class `Note` type for broad Mastodon
interoperability and contain:

- A stable `id` under `/activitypub/posts/`.
- `attributedTo` pointing to the local actor.
- The post publication timestamp.
- Simple, sanitized HTML content containing the title, the first prose
  paragraph capped at 300 Unicode characters, and a visible link to the
  canonical article. Truncation will prefer a word boundary and fall back to a
  character boundary for text without whitespace-delimited words. A spaced
  Unicode ellipsis (` …`) will be appended whenever any article content is
  omitted, including when the complete first paragraph fits under the limit.
- A `url` pointing to the canonical blog post.
- Public addressing, with the ActivityStreams public collection in `to` and
  the local followers collection in `cc`.
- Hashtag objects derived from the post's existing tags. Links and hashtags
  that occur within the excerpt will remain intact rather than being cut by
  truncation.
- When the post has a meaningful image, an ActivityStreams attachment for its
  first such image, including alt text. Images without alt text will not be
  attached.
- A `replies` link pointing to the Worker's collection for this post.
- `likes` and `shares` links pointing to the Worker's collections for this
  post.

The outbox will contain stable `Create` activities wrapping these notes. It will
be paginated and include the complete non-redacted archive. Old activities are
available for clients to read but are marked as already observed when the
Worker is first enabled, so they are not pushed to followers.

The canonical link and the blog page's existing metadata will allow clients to
generate their normal link preview. The ActivityPub HTML will remain
deliberately small and will not attempt to reproduce the article's layout or
full body.

### Follows and delivery

For an inbound `Follow`, the Worker will:

1. Validate the request digest, timestamp, and HTTP signature.
2. Confirm that the signing key belongs to the claimed remote actor.
3. Confirm that the Follow targets the local actor.
4. Resolve and store the remote actor's inbox or shared inbox.
5. Deliver a signed `Accept` containing the original Follow.

A valid `Undo` of a known Follow removes the active follower while preserving
the historical delivery ledger needed for a later redaction.

On each scheduled run, the Worker will compare the live manifest with D1. For
each eligible post, it will create delivery records grouped by remote shared
inbox and send the same stable, signed `Create` activity to each destination.
Retries reuse the same activity identifier and body so receiving servers can
deduplicate them. Temporary failures use bounded exponential backoff; permanent
failures are retained for inspection but are not retried forever.

### Replies

The inbox will accept a signed public `Create(Note)` only when:

- The activity's actor matches the verified signing identity.
- The note's `attributedTo` matches that actor.
- `inReplyTo` identifies one of this site's known, non-redacted ActivityPub
  post objects.

D1 will retain the reply object URL, actor URL, parent post ID, and receipt
time. It may retain the original activity for diagnostics, subject to a size
limit, but the blog will not render or trust its HTML content.

`/activitypub/replies/<source-id>` will expose a paginated collection of the
verified remote reply object URLs. This lets clients such as Mastodon fetch
known replies when resolving a thread. ActivityPub cannot guarantee that this
server will learn about every reply or that every remote instance will display
the same complete conversation.

### Likes and boosts

People must be able to use the normal like and boost controls for a post in an
ActivityPub client. A boost is represented by an `Announce` activity.

The inbox will accept a signed `Like` or `Announce` only when its actor matches
the verified signing identity and its object is one of this site's known,
non-redacted post objects. A valid `Undo` from the same actor will reverse the
corresponding interaction. Activity IDs and D1 uniqueness constraints will
make repeated delivery idempotent.

The Worker will expose `likes` and `shares` collections for each post. These
collections will publish aggregate `totalItems` counts but will not expose a
public list of actors or raw activities. Mastodon and other remote servers
remain responsible for showing the interaction in their clients and for
delivering a boost to the boosting actor's followers.

### Redaction

Redaction must be explicit. A missing Markdown file or missing manifest entry
will never, by itself, cause a federated deletion. This avoids turning a broken
build or accidental file removal into an irreversible protocol action.

The repository will contain an explicit tombstone record keyed by the stable
source ID. When the generated manifest marks a post as redacted:

- A pending, undelivered announcement is cancelled.
- A delivered post causes the Worker to send a signed `Delete` to every inbox
  that previously received it, including destinations that no longer have an
  active follower.
- The post is removed from the public outbox.
- Its ActivityPub object is replaced with a `Tombstone` representation.
- D1 retains enough identity and delivery metadata to prevent accidental
  republication and to make deletion retries possible.

This is a best-effort protocol deletion. It cannot remove screenshots, archives,
or copies retained by non-compliant servers.

### Cloudflare configuration

The existing Pages project remains connected to GitHub. Its supported runtime
configuration and `_build` output directory will be captured in a root Wrangler
configuration file, initially downloaded from the existing project rather than
recreated from memory.

The Python Worker will live in an `activitypub/` directory with its own Wrangler
configuration and D1 migrations. A second Cloudflare Git integration will build
that directory when Worker code changes. Its routes, cron schedule, compatibility
date, non-secret variables, and D1 binding will be defined in the repository.

GitHub authorization, Cloudflare resource creation, resource identifiers, and
secret values necessarily remain external. In particular, the private signing
key must never be committed. Moving the entire deployment into GitHub Actions
is not required for this work.

### Testing

Pure `pytest` tests will cover object construction, excerpt selection,
Unicode-aware truncation and ellipsis behavior, preservation of links and
hashtags, image attachment and alt text, manifest comparison, signature
canonicalization, scheduling, retries, reply validation, like and boost
handling, and redaction decisions. Time and outbound fetching will be
injectable so these tests remain fast and deterministic.

Black-box integration tests will run the production Worker build using
`pywrangler dev`, a temporary local D1 database, test signing keys, a generated
static site, and a small fake remote ActivityPub server. The suite will exercise:

- WebFinger and actor discovery.
- A signed Follow followed by a correctly signed Accept.
- Rejection of invalid signatures, stale dates, invalid digests, oversized
  activities, and unknown actors or posts.
- The 15-minute grace period using an explicitly simulated scheduled-event
  time, without sleeping.
- Delivery of exactly one stable Create activity and idempotent retries.
- Receipt of a signed reply and its appearance in the replies collection.
- Receipt and undoing of signed Like and Announce activities, with accurate
  aggregate counts.
- Explicit redaction, Delete delivery, and the resulting tombstone.

The integration suite must not contact production D1 or live Fediverse
services.

## Cross cutting concerns (as needed)

### Security

ActivityPub inboxes accept requests from arbitrary internet hosts. The Worker
will impose request and stored-payload size limits, validate content types,
require fresh signed dates and valid digests, and compare claimed actors with
their signing keys. Remote actor and key fetches will use HTTPS, bounded
redirects, timeouts, response-size limits, and protections against requests to
private or link-local destinations.

Outbound signatures will initially use the legacy RSA-SHA256 HTTP Signature
format required for compatibility with current Mastodon versions. Signature
code will be isolated so RFC 9421 HTTP Message Signatures can be added later.
Private key material will only be available as a Worker secret.

### Reliability and observability

Network delivery is at-least-once, not exactly-once. Stable activity IDs,
unique D1 constraints, and idempotent state transitions will make retries safe.
Delivery attempts and terminal failures will be queryable in D1 and visible in
Worker logs. A failure delivering to one server must not block delivery to
others.

The scheduled job must use bounded batches so a large follower set or retry
backlog cannot exceed one Worker invocation's limits.

### Data retention and moderation

Follower actor and inbox URLs are operational data and will be retained while a
follow is active. Historical destination URLs are retained for deletion
delivery. Remote reply content will not be displayed by the blog. Reply
references can be removed administratively if they are abusive or invalidated,
without adding a public moderation interface. Likes and boosts will be retained
only as the identifiers and actor relationships needed for idempotency, undo,
and aggregate counts; their public collections will not identify the actors.

## Alternatives considered (as needed)

### Static actor and outbox only

Static documents could make the account and old posts discoverable, but they
cannot complete follows or push new posts to follower inboxes. This does not
meet the notification goal.

### Bridgy Fed or another hosted bridge

A hosted bridge would require much less protocol code and may support more
Fediverse features. It conflicts with the self-contained and learning goals and
places identity and delivery behaviour under a third party's control.

### Cloudflare Pages Functions

Pages Functions could handle the HTTP endpoints close to the existing static
site, but they are JavaScript-oriented and do not provide the scheduled Python
publisher desired here. A separately routed Python Worker keeps the static site
unchanged and supports cron triggers and D1.

### TypeScript Worker

TypeScript has the more mature Workers toolchain and calls Web Crypto directly.
Python keeps the application and tests in one language and can still call the
same native Web Crypto implementation through Pyodide FFI. The remaining beta
risk is acceptable for this personal, non-critical project.

### Publish from the Pages build or GitHub

Triggering delivery from a build couples a pure site build to external side
effects and can announce URLs before a deployment is live. Polling the deployed
manifest is simpler and ensures only successfully published content is
federated.

### General-purpose ActivityPub server or framework

A complete server would offer much broader protocol coverage but would add
substantial dependencies, concepts, and maintenance burden unrelated to this
single feed.

## Implementation (ephemeral)

Implemented locally on 2026-08-24:

- `sitegen/activitypub.py` generates the `Service` actor, stable Notes and
  Create activities, paginated outbox, deployment manifest, explicit
  tombstones, and Pages `_headers` rules. The existing post loader now retains
  source Markdown for deterministic excerpt and attachment extraction.
- Excerpts use the first prose paragraph, preserve links, truncate at a
  Unicode character/word boundary, and append ` …` whenever more content
  remains. The first image with non-empty alt text is attached. Hashtags are
  derived from existing post tags.
- `activitypub/worker/` implements WebFinger, signed inbox validation, follows
  and Accept delivery, replies, likes, announces and Undo, aggregate
  collections, manifest polling, the 15-minute grace period, bounded retries,
  and explicit Delete delivery. WebCrypto is accessed through Pyodide FFI.
- `activitypub/worker/models.py` uses strict Pydantic discriminated unions and
  aliases for inbound activities, remote actors and keys, deployed Notes, and
  manifest entries. ActivityPub models retain unknown extension fields; the
  manifest and redaction formats reject them. Multi-column post and delivery
  query results use small strict Pydantic row models containing only consumed
  fields and tolerating other table columns; scalar queries and writes retain
  the direct D1 helpers.
- `activitypub/migrations/0001_initial.sql` defines the D1 state and delivery
  ledger. `activitypub/wrangler.toml` captures routes, cron, variables, and the
  D1 binding, with the production D1 UUID intentionally left as a placeholder.
- A new RSA keypair was generated. `activitypub/public-key.pem` is committed
  input for the static actor; `activitypub/private-key.pem` is permission
  restricted and ignored, along with `.dev.vars` and local Wrangler state.
- `activitypub/README.md` documents public-repository safety, setup, local
  development, redaction, retries, and basic operations.
- Unit/build tests cover object generation, excerpts, links, images,
  tombstones, signatures, Pydantic deserialization and invariants, inbox
  validation, scheduling helpers, URL safety, and the D1 migration. A
  conditional black-box test covers Follow/Accept,
  simulated scheduled time, grace-period Create, Like, reply collections, and
  redaction/Delete using `pywrangler dev`, local D1, WebCrypto, and a fake
  remote server.
